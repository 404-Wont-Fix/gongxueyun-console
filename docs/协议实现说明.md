# 协议实现说明

本文说明 `backend/app/gxy/` 与 `backend/app/services/` 里的每个请求**依据什么**实现，
以及哪些地方刻意与公开项目不同。

> 证据等级：
> **A** = 开发阶段保存的 APK 反汇编/反编译片段可直接读到（分析产物不随此独立仓库分发）；
> **B** = 仅来自参考仓库源码（可能有效，但未经服务端验证）；
> **U** = 未知，代码中保留为可配置项或明确 fail-closed。

## 2. 加密与签名（A）

```
E(s)   = lowercase_hex( AES-128-ECB( UTF8(s), key = "23DbtQHR2UMbH6mJ", PKCS7 ) )
SIG(x) = md5_hex( concat(x) + "3478cbbc33f84bd00d75d7dfa69e0daa" )
```

- `E` 用于 `phone / password / t`；空字符串在入口短路为 `""`。
- `SIG` 的参数顺序**按调用点**决定，不是对 JSON 排序。
- 验证码临时材料使用服务端返回的 `secretKey`，输出 **Base64**（不是账号字段的 hex）：
  - 校验：`pointJson = E_b64(interaction_json, secretKey)`
  - 结果：`captcha = E_b64(token + "---" + interaction_json, secretKey)`

实现：`backend/app/gxy/crypto.py`。测试：
`backend/tests/test_crypto.py`（含与 Node `crypto` 独立交叉验证的向量）。

## 3. 公共请求封装（A）

`NetUtil.post` → `CommonReqObj.reset` → `baseOption` → Dio：

| 环节 | 行为 | 地址 |
|---|---|---|
| 计算签名 | 页面把业务字段交给 `postSign` | `0xc63db8`（getSign） |
| 补 `t` | **在签名之后**写入 `E(毫秒时间戳)` | `0xd73450` / `0xd734e4` |
| 公共头 | `Authorization`、`userId`、`roleKey`、`devices`、`packageVersion`、`buildNumber`、`codeVersion`、`Client_Id` | `0xd72cf8` |

因此本仓库的 `GxyClient._post` 也是**先算 sign，再加 t**；写操作不做盲目重试。
登录验证码请求使用独立 `HttpManager`（`0xea2850`），不自动补 `t/sign`，本仓库按
`with_t=False` 处理。

## 5. 响应语义（A + 修正）

`savePost` 回调 `0xec8e78` 先比较 **`msg` 字符串**，前提是业务 `code == 200`：

| 条件 | APK 行为 | 本仓库行为 |
|---|---|---|
| `msg=302` | 打开点选验证码，重试保存 | 自动识别（需要模型）或交给验证中心手动点选；重试后重新解释 |
| `msg=303` | 弹窗提示“人脸检测”，确认后调用 `alipayFace 0xec8440`，构造 `alipays://...?query=key1=value1&alipayToken=<token>` | 暂停；只有当响应 `data` **像 token** 时才生成本地链接，否则提示去官方 APP |
| `msg=304` | 弹窗提示“人脸认证”，确认闭包 `0xece90c` → `searchAlipayAnxin 0xec7d00` → `createAxdjk` | 调用 `createAxdjk` 取 `registerUrl/outRegisterNo`，等待本人验证后查询并续提一次 |
| 其他 + `code=200` | 进入普通成功分支，读取 `data.attendanceId` | **不直接报成功**：回查 `listSynchro`，命中才算 success |
| `code!=200` | 由网络层处理 | `rejected`，带原始 code/msg |

这一条是刻意的：27xk 的分支在 `code=200,msg=303` 时没有对应处理，会落进成功；
Rensr0 / maserpoassr 的提交函数也没有 303/304 分支。本仓库把这些都视为“未完成”。

### 303 与 304 的区别（重要）

- **303**：`0xec8fe4` 的默认文案是“系统检测为风险学生,请完成人脸检测识别打卡”，
  `data` 被当作 `String?` 显示。确认后 `0xec8440` 使用 `alipayToken=` 打开支付宝小程序
  (`appId=2021006127602453`)。
- **304**：`0xec910c` 的默认文案是“请完成人脸认证识别打卡”，确认后走
  **createAxdjk → 本人验证 → queryAxdj(outRegisterNo)**。

所以本仓库不会从 303 的中文提示里拼 `alipays://` 链接——tangqingfeng7 的
`:1084–1099` 会把任意 `data` 当 `alipayToken`，中文提示也能通过它的长度检查，
这是一个可复现的假链接风险。我们只接受无空白、无 CJK、≤512 字符的 token 形状。

## 6. 考勤请求模型（A）

54 键来自 `_$AttendanceModelToJson 0xc7d7ec`。本仓库的关键默认值：

| 字段 | 值 | 依据 |
|---|---|---|
| `type` | `START` / `END` / `HOLIDAY` | 序列化模型及 `attendance_type_widget` 选择逻辑，详见休息节假日打卡说明 |
| `state` | `NORMAL` | 同上 |
| `country` | `中国` | 参考实现一致 |
| `createTime` | 当前本地时间 `%Y-%m-%d %H:%M:%S` | 参考实现一致 |
| `attendenceTime` | 默认与 `createTime` 相同；可关闭 | 27xk `:1013`、tangqingfeng7 `:1060` |
| `attendanceType` | 补卡时 `REPLACE`，否则 `null` | 27xk `:1009` |
| `isReplace` | 补卡时也为 `null` | 27xk `:1007`、tangqingfeng7 |
| `appUuid` | 首次 `null`；302 重试时用验证码 `clientUid` | kaka-niu `:514` |
| `isFirstSignInWeb` | `null` | 27xk（tangqingfeng7 写 0，二者都可配置） |
| `captcha` | 302 通过后的证明 | `0xea4ea4` / `0x1100de0` |
| `outRegisterNo` | 304 验证后的登记号 | `0xf2b54c` |
| `t` | 网络层最后添加 | `0xd73450` |

签到签名固定取 `device`(页面设备状态，默认 `mobile`)、`type`、`planId`、`userId`、`address`；
任一为空时本仓库**不发请求**，直接报“参数不完整”，避免生成无意义签名。

## 7. 报告模型（A）

- 60 键来自 `_$ReportModelToJson 0x96262c`。
- `formType`：`day=7, week=8, month=9, summary=10`（Smi 14/16/18/20 还原）。
- 签名：`userId, reportType, planId, title`（`0x1307c50–0x1307d30`）。
- 周期字段按类型区分（A + B）：
  - 日报：只写 `reportTime`，不传 `startTime/endTime`；
  - 周报：`startTime` 周一 00:00:00、`endTime` 周日 23:59:59、`weeks="第N周"`；
  - 月报：`yearmonth="YYYY-MM"`；
  - N 取远端已提交周报的最大编号 + 1（Huee `weekly_report.py:120–128`、27xk `:761`）。
- 修改报告走 `v3/update`，不把 `save` 当万能接口。
- 学校动态表单通过 `paper/v2/info` 拉取后存入草稿，**不盲填**（27xk 会统一写 `"b"`）。

## 8. 验证码

| | 登录滑块 | 打卡点选 |
|---|---|---|
| 类型 | `blockPuzzle` | `clickWord` |
| 识别 | OpenCV Canny + matchTemplate（纯本地） | ONNX YOLOv5n + OCR（可选） |
| 无模型时 | 不适用 | 验证中心展示图片，由用户按顺序点击 |
| 坐标 | `{"x":距离,"y":5}` | `[{"x":..,"y":..}]` |
| 加密 | `E_b64(interaction, secretKey)` | 同左 |

点选验证码的图片会返回给前端**仅用于本人点击**；`secret/token` 不出库、不出接口。
坐标以图片原始像素提交（前端按 `naturalWidth` 换算）。

## 9. 与参考项目的主要差异

| 参考实现 | 问题 | 本仓库做法 |
|---|---|---|
| 27xk / tangqingfeng7 成功分支 | 依赖 `code==200`，303 可能被当成功 | 302/303/304 全部单独状态，成功必须记录回查 |
| tangqingfeng7 303 | 中文提示也能拼出 `alipays://` 链接 | token 形状校验，否则只给提示 |
| tangqingfeng7 queryAxdj | 缺公共 `t` | 统一补 `t`（与 APK `0xd73450` 一致） |
| 多数项目 | 写请求自动重试 | 写请求不重试；刷新 token 后也只重发一次 |
| kaka-niu / JiangRTTTR | 304 交给点选验证码 | 304 走登记 + 查询 + 单次续提 |
| 27xk 表单 | 统一填 `"b"` | 拉取真实字段，交用户填写/确认 |
| 旧项目 | 明文密码、日志含 token | 密码/会话/token 一律加密存储，日志只记状态 |
| 旧项目 | 只改 URL 版本号 | 版本、UUID、字段、签名按 APK 调用点分别实现 |

## 10. 仍未确认（U）

1. 服务端真实必填字段与对所有 `null` 的容忍度；
2. 303 的 token 究竟来自哪个存储（APK 弹窗只显示提示文本）；
3. 304 续提时服务端是否一定接受 `outRegisterNo` + 原 body；
4. 学校动态表单的校验规则、附件与图片要求；
5. 教师角色、补卡审批、跨月/跨年周期；
6. 频控阈值、IP 风控与同设备多账号策略。

这些未知项不能被本地测试消除。尤其是 303 token 形状判断并不证明它的真实来源，验证续提流程仍需授权的真实环境核验。
